# AgentDock Desktop

A thin Electron shell around the AgentDock web UI. Launching the app is enough:
it starts a bundled daemon on a stable loopback port, waits for `/health`, and
loads the normal console. Closing the window stops the daemon and every agent
process below it.

## Why Electron

AgentDock's server is a Node bundle with native modules (`better-sqlite3`,
`node-pty`) that spawns agent CLIs. Electron lets us ship one runtime that hosts
both the UI and the server; Tauri would still need a Node sidecar plus a second
IPC layer. electron-builder also gives installers and macOS/Windows signing with
no custom tooling.

## Development

```bash
pnpm build
pnpm --filter @agent-dock/desktop dev
# point at a different build / Node binary:
AGENTDOCK_DESKTOP_CLI=$PWD/apps/server/dist/cli.js \
AGENTDOCK_DESKTOP_NODE=$(which node) \
pnpm --filter @agent-dock/desktop dev
```

Dev mode uses the workspace build directly; no runtime assembly is needed.

## Packaging

```bash
pnpm build
# local, using the current Node (not a downloaded copy):
AGENTDOCK_DESKTOP_NODE_BIN=$(which node) pnpm --filter @agent-dock/desktop pack:dir
# production installers (downloads Node 24.16.0 for the current platform):
pnpm --filter @agent-dock/desktop dist
```

`scripts/prepare-runtime.mjs` runs `pnpm deploy --prod --legacy` for
`@agent-dock/cli` (keeping the workspace's patched acpx and Lark SDK) and puts a
standalone Node binary next to it. Both are bundled through `extraResources`.

Outputs land in `apps/desktop/release/`.

## Auto-update

Packaged builds use `electron-updater` with the GitHub Releases feed declared
in `electron-builder.config.cjs`. The sidebar entry shows the detected version,
the download percentage and speed, and a final “重启并安装” action. Update files
(`latest-mac.yml` / `latest.yml`, blockmaps) are generated by electron-builder
and uploaded next to the installers by `.github/workflows/desktop.yml`. Beta
tags are published as GitHub prereleases, so stable clients never pick them up.

The check runs shortly after launch and every four hours, plus on demand from
设置 → 检查更新. Downloads never start without the user clicking; the app never
installs an update on quit unless “重启并安装” was confirmed.

### Signing: one fixed certificate for every release

macOS auto-update requires the new bundle to match the running app's code
signing identity. Ad-hoc signatures use the build's cdhash as the designated
requirement, so every new build fails verification and updates silently break.
A **fixed self-signed certificate reused across releases** satisfies the check
(Developer ID + notarization is nicer, but not required for the updater):

```bash
pnpm --filter @agent-dock/desktop signing:generate
```

The script writes `apps/desktop/.signing/` (gitignored) and prints the base64
p12 plus the generated password. Store them as GitHub Actions secrets:

| Secret | Value |
| --- | --- |
| `MAC_CERT_P12` | contents of `agentdock-signing.p12.base64` |
| `MAC_CERT_PASSWORD` | printed password |

Keep the certificate and password forever — replacing the p12 breaks
auto-update for already-installed clients (they need one manual reinstall).
With the self-signed identity the first install still requires the usual
“隐私与安全性 → 仍要打开” approval; subsequent updates install in-app. If
`MAC_CERT_P12` is absent the build falls back to ad-hoc signing and the updater
cannot install on macOS (Windows NSIS updates work without signing).

### Local smoke test

```bash
pnpm build
pnpm --filter @agent-dock/desktop smoke:update
```

This starts a mock generic update feed on `127.0.0.1`, launches the real shell
against a disposable profile, and captures two screenshots under
`apps/desktop/.smoke/`: one with “新版本可用”, one with the download progress
percentage. The fake archive is never installed.

## Mobile access (LAN + public URL)

The phone icon at the bottom of the sidebar issues an **app-level** link
(the same master token type as the console link printed at startup): scanning it
grants full control of the console, and it expires after the master token TTL
(365 days by default). Treat the QR as a login credential and never share it.

The shell listens on loopback by default, but the web gate is **always on**:
loopback requests pass as the machine owner (no password prompt), while a
rebound domain, a cross-site page, or a forwarded tunnel request cannot. The QR
dialog can enable **局域网访问**: that writes `lanAccess: true` to
`settings.json`, restarts the bundled daemon with `--host 0.0.0.0`, and leaves
authentication unchanged. Existing agent tasks are interrupted by the restart.
Anonymous LAN requests get 401; the local window keeps working.

The backend still accepts an optional `https://` public base URL (persisted in the
database; `AGENTDOCK_PUBLIC_URL` overrides it), but the public-URL input is
**hidden in the UI for now** while that flow is reworked. AgentDock deliberately
does **not** create the tunnel itself. For later reference, a safe setup on a
laptop:

```bash
# 1. Install cloudflared, then authenticate (opens a browser).
cloudflared tunnel login
cloudflared tunnel create agentdock

# 2. ~/.cloudflared/config.yml
# tunnel: <TUNNEL_ID>
# credentials-file: /Users/you/.cloudflared/<TUNNEL_ID>.json
# ingress:
#   - hostname: dock.example.com
#     service: http://127.0.0.1:4310
#   - service: http_status:404

# 3. Point DNS at the tunnel and run it.
cloudflared tunnel route dns agentdock dock.example.com
cloudflared tunnel run agentdock
```

Then create a **Cloudflare Access** self-hosted application for
`dock.example.com` with an allow policy (email, SSO, or service token). Access
authenticates the person at Cloudflare's edge; AgentDock still requires the
app-level token carried by the QR, so both layers apply. Finally enter
`https://dock.example.com` under 公网访问 in the QR dialog.

Notes:

- Because cloudflared runs on the same machine, it can reach
  `127.0.0.1:4310` even when the shell stays in loopback-only mode. The public
  URL therefore works without enabling LAN access.
- **Do not use `trycloudflare.com` quick tunnels** for a long-lived AgentDock
  instance: the URL is public, randomly reassigned, and has no edge
  authentication — the app-level token would be the only barrier.
- A domain hosted in Google Cloud DNS can be used the same way after delegating
  a subdomain (NS records) to Cloudflare. Running AgentDock on a GCP VM behind
  an HTTPS load balancer + Identity-Aware Proxy is the other option, but that is
  a server deployment, not a tunnel to a laptop.
- `AGENTDOCK_PUBLIC_URL` is validated as an `https://` URL; plaintext public
  links are rejected.

```bash
pnpm --filter @agent-dock/desktop smoke:lan
```

This launches the real shell twice with disposable profiles: once with
`lanAccess: true` (loopback 200, LAN 401) and once with `lanAccess: false`
(loopback 200, LAN connection refused). It never touches the installed app.

## CI / signing

`.github/workflows/desktop.yml` builds macOS (arm64 + x64) and Windows x64 on
native runners. Linux has no desktop shell; it uses the CLI + Web UI. Tag `v*`
publishes a GitHub Release whose body links the matching npm package and whose
assets are the installers. The workflow verifies every macOS bundle with
`codesign --verify --deep --strict` and fails if a configured certificate did
not produce a Developer ID signature.

### macOS

electron-builder selects the signing mode automatically:

| Situation | Result |
| --- | --- |
| `CSC_LINK` + `CSC_KEY_PASSWORD` (CI) | Developer ID Application signature |
| `CSC_NAME`, or a Developer ID identity in the keychain (local) | Developer ID Application signature |
| neither | ad-hoc signature (`-`) |

Ad-hoc signing is the default when no certificate exists. It matters: renaming
`Electron.app` invalidates the framework's original linker signature, and macOS
then reports the app as *damaged*. An ad-hoc signature keeps the bundle
structurally valid and signs the bundled Node runtime and native modules too, so
the app launches. It is still **not notarized**, so recipients see “Apple could
not verify … is free of malware” and must allow the app once via System
Settings → Privacy & Security → Open Anyway (or right-click → Open).

Gatekeeper-clean distribution needs the paid Apple Developer Program
(US$99/year): create a **Developer ID Application** certificate and export it
as `.p12`. Notarization then needs either an Apple ID app-specific password or
an App Store Connect API key.

| Secret | Value |
| --- | --- |
| `MAC_CERT_P12` | base64-encoded `.p12` |
| `MAC_CERT_PASSWORD` | `.p12` export password |
| `APPLE_ID` / `APPLE_APP_SPECIFIC_PASSWORD` / `APPLE_TEAM_ID` | notarization via Apple ID |
| `APPLE_API_KEY_P8` / `APPLE_API_KEY_ID` / `APPLE_API_ISSUER` | notarization via App Store Connect API key (`.p8`, base64) |

The certificate secrets sign; the `APPLE_*` secrets notarize. Setting only the
certificate produces a valid but unnotarized app. Locally, export
`CSC_NAME="Developer ID Application: …"` and the same `APPLE_*` variables
before `pnpm dist`.

### Windows

- `.pfx` certificate: `WIN_CERT_P12` + `WIN_CERT_PASSWORD`. OV certificates
  satisfy SmartScreen only after reputation accumulates; EV certificates are
  trusted immediately but cost more.
- Azure Trusted Signing (no `.pfx`): set `AZURE_SIGNING_ENDPOINT`,
  `AZURE_SIGNING_ACCOUNT`, `AZURE_SIGNING_PROFILE`, optionally
  `AZURE_SIGNING_PUBLISHER`, plus Entra service-principal credentials
  `AZURE_TENANT_ID`, `AZURE_CLIENT_ID`, `AZURE_CLIENT_SECRET`. electron-builder
  installs the `TrustedSigning` PowerShell module on the runner itself.
- OSS projects can apply for free signing through SignPath.

Linux AppImage is not code signed; publish a SHA-256 checksum with the release.
Native modules and the bundled Node runtime are architecture-specific, which is
why each arch is built on a matching runner instead of cross-compiled.

## Runtime layout

```
AgentDock.app/Contents/Resources/
  agentdock/       @agent-dock/cli dist + node_modules + public/
  node-runtime/    node (or node.exe)
```

User data (database, logs, window state) lives under Electron's `userData`
directory (`~/Library/Application Support/AgentDock` on macOS).
